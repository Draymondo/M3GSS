# M3GSS

> **M3GSS (personal project) — local/offline AI image reconstruction and upscaling, inspired by the DLSS concept.**

M3GSS is a personal, low-cost / zero-budget research project whose real objective is **not merely to maximize PSNR**: the final target is a useful **real-time image reconstruction/upscaling pipeline for games on a GTX 970 4 GB**, with practical GPU cost and no dependence on a cloud service at runtime.

The project is currently moving from **offline model validation** toward the **real-time runtime / game integration phase**.

---

## 1. Project goal

The intended end state is conceptually:

```
Game renders lower resolution
        ↓
   M3GSS reconstruction
        ↓
Higher-resolution reconstructed frame
        ↓
      Display
```

First practical target:

- input: approximately 960×540
- reconstruction: ×2
- output: approximately 1920×1080
- target hardware: **NVIDIA GTX 970 4 GB**
- priority: **quality × latency × FPS**, not PSNR alone.

The first game-facing implementation should be treated as a **runtime prototype** before attempting deep integration into a game's graphics pipeline.

## 4. Current model architecture

Model:

`M3GSS_v0_32x8`

Parameters: **158,979**

Architecture:

1. RGB input
2. `Conv2d(3, 32, 3×3, padding=1)`
3. LeakyReLU(0.1)
4. 8 residual blocks:
   - Conv 3×3 → LeakyReLU → Conv 3×3
   - local residual skip
5. trunk Conv 32→32
6. global skip from the head
7. zero-initialized final Conv 32→3
8. predicted residual added to the bicubic input

Current architectural constraints:

- **no BatchNorm**
- **no attention**
- **no PixelShuffle**
- small/lightweight CNN
- residual reconstruction on top of bicubic input

×2 pipeline:

- HR patch: **96×96**
- LR patch: **48×48**
- LR generated by area downscaling
- bicubic baseline generated with the project's Catmull-Rom bicubic implementation
- network predicts a residual over that bicubic reconstruction.

## 5.1. Historical training chronology and clarified context

The training history is important because the project went through more than one data-availability stage.

### Stage A — initial DIV2K-only work
The first local training work was started with **DIV2K train_HR (800 images)**. There was an earlier DIV2K-only run for which the captured output was incomplete; it should **not** be confused with the official V0 benchmark below.

### Stage B — Flickr2K added locally
After Flickr2K became available locally, the training pipeline was extended to use:

- 800 DIV2K training images
- 2,650 Flickr2K HR images
- **3,450 training images total**

This combined dataset is the dataset configuration associated with the official V0 training result recorded in this README:

- 5,000 steps
- batch 8
- learning rate 1e-4
- GTX 970
- checkpoint names: `m3gss_v0_big_latest.pt` / `m3gss_v0_big_best.pt`
- 5,708.28 s (~1 h 35 min)
- 0.88 step/s.

The important historical point is therefore:

`DIV2K-only preparation → Flickr2K added → combined 3,450-image training → V0 validation → V1 loss experiment`

There is **no reliable evidence in the recovered project history for treating the earlier incomplete DIV2K-only run as the official V0 result**.

### Stage C — V1
V1 kept the same lightweight architecture and combined 3,450-image dataset while changing the loss to Charbonnier + edge gradient loss. The official local V1 result is the 5,000-step GTX 970 run documented in Section 6.

### Stage D — Kaggle
Kaggle was subsequently used as an additional experimentation environment. It reproduced the same 800 + 2,650 image dataset configuration, but the 5,000-step Kaggle run was interrupted by a session reset and is **not an official completed training result**.

### Why this distinction matters
Another AI agent should not infer that every mention of a 5,000-step run refers to the same experiment. The project contains:

1. an early incomplete DIV2K-only run,
2. the official combined-data V0 result,
3. the official combined-data V1 result,
4. an incomplete Kaggle experiment.

Only the completed local GTX 970 V0/V1 results should currently be treated as established project benchmarks.

## 6. V1 — Charbonnier + Edge/Gradient loss

V1 keeps the **exact same neural architecture**. The training objective changed.

Constants:

- `CHARBONNIER_EPS = 1e-3`
- `EDGE_WEIGHT = 0.1`
- `LOSS_VERSION = "v1_charbonnier_edge"`

Loss:

```
Charbonnier = mean(sqrt(diff² + eps²))
Edge = L1 difference between x/y image gradients
Total = Charbonnier + 0.1 × Edge
```

The implementation includes a small-image guard for the gradient term.

Tests covered:

- identical tensors
- constant offsets
- finite/non-zero backward gradients
- tiny spatial dimensions.

### Official V1 GTX 970 result

- 5,000 steps
- architecture unchanged
- batch 8
- LR 1e-4
- HR patch 96×96
- ×2
- Charbonnier eps 0.001
- Edge weight 0.10
- GTX 970 4 GB

Training:

- Charbonnier: **0.016299**
- Edge: **0.039409**
- Total: **0.020240**
- time: **3451.96 s** (~57 min 32 s)
- speed: **0.87 step/s**
- peak VRAM: **258.1 MiB**

Official validation:

| Model | PSNR |
|---|---:|
| Bicubic | 31.2474 dB |
| M3GSS V0 | 32.7892 dB |
| M3GSS V1 | **32.7649 dB** |

V1 gain vs bicubic: **+1.5176 dB**

V1 vs V0: **−0.0243 dB**

Visual conclusion:

- V1 reduces ringing and oversharpening seen in V0
- contours are more stable
- repetitive/fine structures look more natural
- slight loss of maximum micro-detail / sharpness in some areas
- V1 is retained as a targeted improvement over V0.

Detailed results: `docs/M3GSS_V1_RESULTS.md`.

## 8. Kaggle DIV2K + Flickr2K experiment

A Kaggle experiment was prepared using:

- 800 DIV2K
- 2,650 Flickr2K
- total 3,450 images
- Tesla T4
- batch 8
- LR 1e-4
- 5,000 steps
- seed 1234
- same V1 Charbonnier + Edge loss.

25-step benchmark after data-loader optimization:

- before: **0.48 step/s**
- after: **0.50 step/s**
- 52.04 s → 49.88 s for 25 steps
- peak VRAM: ~297.1 MiB

Optimization:

- parallel sample preparation
- up to 8 worker threads
- thread-local ZIP handles
- Flickr2K stays compressed.

Reproducibility note:

- the parallel loader changed exact random crop RNG consumption compared with the older implementation.
- architecture, loss, hyperparameters and dataset protocol remain the same, but the exact sample/crop sequence is not guaranteed to match the earlier local run.

The Kaggle 5,000-step run was **not completed** after a Kaggle session reset. The repo and Flickr2K archive had to be restored. Checkpoint/resume support already exists in `ml/train.py`.

**Kaggle training is not currently the highest priority.** The project priority has shifted to runtime/inference on the GTX 970.

## 12. Performance observations

### GTX 970

The GTX 970 is the final target.

Observed local training:

- ~0.87–0.88 step/s for batch 8
- ~258 MiB peak allocated VRAM
- model size: 158,979 parameters.

### Tesla T4

The T4 did not produce the huge training speedup expected from GPU specifications alone.

Optimized Kaggle pipeline: approximately **0.50 step/s**.

Training throughput is strongly affected by CPU/data preparation, ZIP decoding and patch construction. T4 training throughput is therefore **not** a proxy for final runtime performance.

## 13. Real project priority — runtime

### Most important next phase

Determine whether the current lightweight network can perform useful reconstruction **in real time on the GTX 970**.

First runtime experiment:

```
960×540 frame
      ↓
M3GSS ×2
      ↓
1920×1080 reconstructed frame
```

Measure:

1. inference latency per frame
2. FPS
3. GPU utilization
4. VRAM usage
5. CPU overhead
6. image quality against bicubic
7. visual artifacts
8. end-to-end latency once a frame source is introduced.

Key metric:

> **quality × latency × FPS on GTX 970**

—not PSNR alone.

### Runtime progression

1. Load the trained V1 checkpoint on ATMOS.
2. Run deterministic single-image inference on GTX 970.
3. Measure latency over many frames.
4. Compare M3GSS against Catmull-Rom bicubic.
5. Test input/output resolutions.
6. Build a continuous frame-processing loop.
7. Then begin game-facing capture/integration.
8. Evaluate real game performance and visual quality.

## 15. Design principles / constraints

M3GSS should remain:

- personal-use focused
- local/offline at runtime
- minimal or zero budget
- lightweight enough for GTX 970 4 GB
- experimentally measurable
- reproducible where practical
- incremental rather than architecture-heavy
- judged by real visual quality and runtime performance.

Do not optimize only for benchmark numbers.

Do not add heavy architecture components without evidence that the current lightweight approach has reached its limit.

Do not treat Kaggle/T4 performance as the final success criterion.
